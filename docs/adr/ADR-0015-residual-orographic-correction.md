# ADR-0015 — Остаточная орографическая коррекция вместо формулы §10.3

| | |
|---|---|
| **Статус** | Accepted (2026-07-27) |
| **Ревизует** | §10.3 п.1 (коррекция температуры) |
| **Реализует** | §10.3 п.2, п.4 (изотерма, фаза осадков), FR-DS-2 |
| **Связан с** | ADR-0017 (высоты по DEM) |

## Контекст

PRD §10.3 предписывает применять к температуре модели орографическую поправку:

```
T_corr = T_model + Γ × (h_dem_model − h_true),  Γ = 0.0065 °C/м
```

Мотивировка в PRD верная: глобальная модель видит вместо Фишта сглаженную
возвышенность, и без поправки все производные величины смещены.

Однако §10.3 писался в предположении, что мы получаем сырое поле модели. На
практике транспорт — Open-Meteo (§8.3 T1), а он **сам выполняет statistical
downscaling к переданному `elevation`**. Проверено замером на одной координате:

| Запрошенный `elevation` | `elevation` в ответе | T_max |
|---|---|---|
| 2391 м | 2391 м | 11.3 °C |
| 1000 м | 1000 м | 20.3 °C |
| не передан | 2281 м | 12.0 °C |

Разница 9.0 °C на 1391 м — это 0.00647 °C/м, то есть ровно тот же стандартный
градиент, что и в формуле PRD. Применение формулы §10.3 поверх этого **удвоило
бы коррекцию**: на Ачишхо (истинная высота 2391, ячейка DEM 2281) мы добавили бы
0.7 °C из ниоткуда. На границе фазы осадков столько решают.

Третья строка таблицы даёт ещё один факт: без явного `elevation` провайдер берёт
2281 м — ровно то значение, которое мы записали в `dem_elevation_m` по итогам
сверки (ADR-0017). Значит наш DEM и его DEM — один и тот же рельеф.

## Решение

Считать **остаточную** поправку — от высоты, которую провайдер вернул в ответе,
а не от высоты ячейки DEM:

```
T_corr = T_model + Γ × (h_provider_ответ − h_true)
```

Когда провайдер послушался нашего `elevation`, поправка равна нулю — и это
нормальный, ожидаемый случай. Когда он высоту проигнорировал, обрезал или не
поддержал для конкретной модели, разница ненулевая, и мы её чиним.

Это ровно то, ради чего в PRD существует **FR-DS-2** («система дополнительно
сохраняет `elevation`, возвращённую провайдером, для контроля»): требование уже
предусматривало, что ответ провайдера надо сверять, — мы лишь используем эту
сверку как источник поправки, а не только как индикатор.

Пункты §10.3, реализованные без изменений:

- **п.2, нулевая изотерма** — считается из скорректированной температуры точки:
  `h_freezing = h_true + T_средняя / Γ`;
- **п.4, фаза осадков** — снег выше изотермы на слой таяния (100 м), дождь ниже
  на столько же, между — мокрый снег. Фаза берётся по **средней** температуре
  суток: по максимуму снег не выпал бы никогда, по минимуму шёл бы каждую ночь.

**п.3 (`k_oro`, орографическое усиление осадков) сознательно не реализован** —
§10.3 прямо требует не подбирать формулу, а обучать множитель по факту в
Accuracy Engine (§10.8.5). Это Фаза 3.

## Последствия

**Плюсы**
- Двойная коррекция исключена конструктивно, а не бдительностью.
- Появились фаза осадков и высота нулевой изотермы — то, ради чего §10.3
  назывался критичным для точек выше 2500 м (Цахвоа, Фишт, Оштен).
- Если провайдер сменится или перестанет делать downscaling сам, формула
  автоматически превратится в исходную §10.3 — менять код не придётся.

**Минусы / риски**
- Мы зависим от того, что провайдер честно сообщает использованную высоту. Если
  он начнёт возвращать запрошенное значение, фактически считая по другому,
  поправка будет нулевой, а ошибка — незаметной. Смягчение: `dem_elevation_m` в
  каталоге даёт независимую опорную точку для сверки.
- Γ фиксирован 0.0065. Фактический градиент из уровней 850/700 гПа (он учитывает
  инверсии, а зимой в котловине Красной Поляны они обычны) — Фаза 2.
- Фаза по средней суточной температуре огрубляет переходные дни: реальный снег
  выпадает ночью и тает днём. Почасовая фаза — вместе с полным HIL (§10.4).
