# ADR-0013 — Хостинг на бесплатном serverless без верификации картой

| | |
|---|---|
| **Статус** | Accepted (2026-07-26) |
| **Заменяет** | ADR-0010 (Cloudflare R2 как объектное хранилище) |
| **Ревизует** | §16 (Облачная инфраструктура), частично ADR-0001 (развёртывание) |
| **Связан с** | ADR-0012 (Telegram webhook), ADR-0009 (PostgreSQL) |

## Контекст

PRD §16 предполагает основной хостинг **Oracle Cloud Always Free** (1× ARM VM,
Docker Compose) и **Cloudflare R2** для объектного хранилища. Оба требуют
**привязки банковской карты для верификации аккаунта**. Владелец проекта не
имеет возможности пройти карточную верификацию и не может оплачивать хостинг.
Это блокер и для GCP/AWS free tier, Fly.io, Cloudflare R2.

При этом фактическая нагрузка MVP — **пакетный конвейер раз в 4 часа** (6 прогонов
в сутки) плюс **Telegram-бот на webhook**. Постоянно живущая VM простаивала бы
почти всё время; событийная нагрузка бота — редкая и короткая. Это профиль,
который дешевле и проще покрывается serverless, чем арендой VM.

## Решение

Отказаться от VM + Docker Compose в пользу **serverless-раскладки на бесплатных
тарифах, не требующих карты**, сохранив основной язык Python (ADR-0002):

| Функция | Было (§16) | Стало |
|---|---|---|
| Планировщик + воркеры конвейера | Oracle VM, APScheduler, Redis Streams | **GitHub Actions** cron (каждые 4 ч) + `workflow_dispatch`. Public-репо → минуты без лимита |
| Реляционная БД | PostgreSQL на VM | **Supabase** (Postgres 16, free) — по умолчанию; альтернатива **Neon** |
| Объектное хранилище raw payloads | Cloudflare R2 | **Supabase Storage** (1 ГБ) или gzip в Postgres `bytea` (§13 и так использует bytea) |
| Бот (интерактивные команды) | aiogram на VM | **Vercel** Python serverless-функция (webhook) или **Deno Deploy** |
| Push-уведомления (алерты) | worker-notify (always-on) | Финальный шаг cron-джоба GitHub Actions вызывает Telegram API напрямую |
| Наблюдаемость | Prometheus/Grafana/Loki на VM | Логи GitHub Actions + Supabase + бесплатный Sentry/Grafana Cloud |

Событийная модель (§11.4) на MVP схлопывается: конвейер — один последовательный
идемпотентный джоб вместо Redis Streams. Порты и модульные границы (§11.3, MB-1..5)
сохраняются — это позволяет вернуть Redis/воркеры позже без переработки домена.

## Последствия

**Плюсы**
- Стоимость $0, регистрация без карты (проверяется при онбординге — политики могут меняться).
- Python и структура модулей PRD сохраняются; конвейер из vertical slice переносится почти как есть.
- Нет эксплуатации VM (патчи ОС, бэкапы, мониторинг демонов).

**Минусы / риски**
- **Notification Latency (§2.2, цель p95 ≤ 15 мин):** cron GitHub Actions неточен и может
  запаздывать на 5–15 мин под нагрузкой → цель на грани. Принимаем как риск MVP.
- Нет Redis-кэша и распределённых блокировок → идемпотентность и «ровно один запуск»
  обеспечиваются на уровне БД (уникальные ключи, `SELECT ... FOR UPDATE`).
- Холодные старты serverless-функции бота (цель ответа ≤ 2 с, FR-TG-7) — приемлемо,
  read-модель отдаётся из Postgres.
- Раздельные площадки (Actions + Supabase + Vercel) вместо единого `docker compose up`
  — сложнее локальная воспроизводимость; компенсируется `.env.example` и общим конвейером.

**План отката:** если появится доступ к VM (напр., GitHub Student Pack → DigitalOcean/
Azure кредиты), возвращаемся к §16 без изменения доменного слоя — меняются только
адаптеры platform-слоя (scheduler, storage, broker).
