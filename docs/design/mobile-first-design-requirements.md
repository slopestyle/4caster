# 4CASTER — требования на mobile-first дизайн (бриф для Claude design)

> Назначение файла: единый бриф для генерации экранов приложения. Вставляется
> в Claude design целиком вместе с [PRD.md](../../PRD.md) (разделы 1, 3, 15).
> Формат вывода — интерактивный HTML-артефакт: галерея экранов в мобильном
> фрейме, светлая и тёмная темы.

## 0. Что проектируем

**4CASTER** — не прогноз погоды, а система поддержки решения «идти в горы или нет»
(Западный Кавказ, Абхазия). Отвечает на три вопроса: **что изменилось** в прогнозе,
**насколько ему можно верить**, **меняет ли это решение о выходе**.

Целевая поверхность — **Telegram Mini App**: мобильный веб, открывающийся внутри
Telegram. Это и есть «вебфронт». Поэтому дизайн **mobile-first** и по умолчанию
одноколоночный; десктоп — второстепенная, расширенная раскладка.

Данные реальные (уже считаются конвейером): локации **Ачишхо (2391 м)**,
**Аибга (2509 м)**, кластер CL-ALP-W. По каждому дню: осадки `p50 (p10–p90)` мм,
вероятность POP %, категория HIL 0–5. Reliability Score — Фаза 2 (пока не число).

## 1. Главный принцип: честность о неопределённости

Это не украшение, а суть продукта. Из него следуют жёсткие правила дизайна:

- **P1. Ни одного числа без меры доверия.** Значение осадков всегда рядом с
  разбросом (`p10–p90`) и/или индикатором надёжности. «12 мм» в одиночку — запрещено.
- **P2. Числа что-то значат.** Reliability 41 сопровождается словами
  («ориентировочно, проверьте через 2 дня»), а не просто цветом.
- **P3. Некалиброванное — не показываем как точное число** (PRD INV-6). Пока
  калибровки нет — надёжность отображается словом/диапазоном/индикатором согласия
  моделей, а не «числом из воздуха».
- **P4. Дальний горизонт визуально «слабее» ближнего.** 10-й день не должен
  выглядеть так же уверенно, как завтра (снижение контраста/насыщенности с ростом
  lead time).

## 2. Платформа и ограничения

| Параметр | Требование |
|---|---|
| Подход | **Mobile-first**, одна колонка. Базовая ширина 360–430 px. Десктоп — max-width ~640 px по центру, либо 2 колонки для дашборда. |
| Telegram Mini App | Учитывать `themeParams` Telegram (цвета берутся из темы клиента); поддержать `viewportStableHeight`, `safe-area-inset`, кнопку `MainButton`/`BackButton` в паттернах. |
| Темы | **Светлая и тёмная** — обе полноценные (Telegram передаёт активную). Не «прикручивать» тёмную, а проектировать сразу. |
| Тач | Минимальная зона нажатия **44×44 px**; основные действия — в нижней трети экрана (большой палец). |
| Ответ | Восприятие «моментально»: скелетоны вместо спиннеров; контент из кэша (карточки уже готовы в БД). |
| Язык | Русский (продукт RU/EN; проектируем RU, строки — не в вёрстке жёстко). |
| Оффлайн/сеть | Явные состояния: загрузка, пусто, ошибка, «прогноз ещё не рассчитан», деградация `N/5 моделей`. |
| Доступность | Контраст ≥ 4.5:1; цвет надёжности **дублируется** формой/текстом (не только цветом) — для дальтоников. |

## 3. Принципы UX (из PRD §15.1, адаптированы под mobile)

1. **Вывод, потом детали, потом сырьё.** Прогрессивное раскрытие: карточка → по тапу
   детали (часы/модели) → по тапу сырые данные моделей.
2. **Кнопки, а не команды.** Основной путь — тапабельные элементы, чипы, свайпы.
3. **Один экран — один ответ.** Первый ответ помещается без прокрутки на телефоне.
4. **Каждое уведомление действенно.** Содержит вывод и рекомендацию, а не только факты.
5. **Молчание — валидный вывод.** «Без изменений 3 дня» — это позитивный, спокойный
   статус, а не пустота.

## 4. Информационная архитектура (экраны)

Нижняя навигация (таб-бар), 4 вкладки + модалки:

1. **Сегодня / Мои точки** (домашний): список локаций/походов с краткой сводкой.
2. **Прогноз** (карточка локации) — ядро, глубокий экран.
3. **Надёжность** — доверие по горизонтам + разложение.
4. **Изменения** — лента значимых изменений и история.
5. Модалки/вложенные: Онбординг, Настройки, Поход (Trip), Сравнение, Окно выхода.

## 5. Требования по ключевым экранам

### 5.1. Онбординг (`/start`)
- 2–3 слайда: суть продукта (не прогноз, а решение), выбор часового пояса, первой
  локации. CTA — Telegram `MainButton` «Поехали».
- Один экран объяснения принципа неопределённости с живым мини-примером.

### 5.2. Домашний «Мои точки»
- Карточки локаций: название + высота, иконка погоды на сегодня/завтра, HIL,
  индикатор надёжности ближнего горизонта, стрелка тренда (лучше/хуже/без изменений).
- Пустое состояние: «Добавьте точку» с крупной кнопкой.
- Поход (Trip) — отдельная карточка сверху: дни до старта, прогноз на даты, надёжность.

### 5.3. Карточка прогноза (ядро) — экв. §15.3
- Шапка: `🏔 Ачишхо · 2391 м · Consensus N/5 моделей`, время обновления, бейдж
  деградации если моделей < 5.
- Список дней (7, расширяемо до 14). Каждая строка:
  - день недели + дата;
  - иконка + подпись HIL («Сильный дождь»);
  - **осадки `p50 (p10–p90) мм`** — p50 крупно, разброс мельче/приглушённо;
  - **бар вероятности POP** (5 делений) + `%`;
  - зона нажатия — раскрывает почасовую детализацию дня.
- Строка надёжности по горизонтам 1/3/7/14 с семантикой цвета (см. §6) — но, пока
  нет калибровки, **со словом-статусом**, не голым числом.
- Предупреждение-плашка (напр. «Сб: гроза 13–18, избегать гребней»).
- Действия (кнопки): Часы 48ч · Модели · Надёжность · История · Окна · Подписаться.

### 5.4. Метеограмма 48ч
- Мобильная, скроллящаяся по горизонтали при необходимости, но помещается по высоте.
- Слои: столбцы осадков `p50` + лента `p10–p90`; линия POP; температура; высота
  нулевой изотермы; **заливка «сухих окон»**; метка пика грозы 13–19ч.

### 5.5. Надёжность (`/reliability`)
- Горизонты 1/3/7/14 сут — крупные «плитки» со статусом.
- **Разложение** на компоненты (согласие моделей, ансамблевый разброс, стабильность
  во времени, историческая точность, предсказуемость) — каждая с однострочным
  человекочитаемым пояснением.
- Рекомендация «когда прогноз устаканится» («станет надёжным ~2 августа»).
- Состояние «калибровка появится в Фазе 2» показать честно, не подделывая число.

### 5.6. Сравнение моделей (`/models`)
- Таблица «модель × день» с весами; на mobile — горизонтальный скролл или карточки
  по моделям.
- Spaghetti-график: линия каждой модели + облако ансамбля + жирная линия консенсуса.

### 5.7. История / эволюция прогноза (`/history`) — «визуальное ядро»
- Heat-map: X — момент выпуска прогноза, Y — валидная дата, цвет — осадки; метки
  отправленных алертов. На mobile — вертикальный приоритет, зум/пан.
- Это то, чего нет у конкурентов, — должно выглядеть «фирменно».

### 5.8. Уведомление об изменении (карточка алерта)
- «Было → стало» для конкретных дат; какие модели «двигали» прогноз; новый статус
  надёжности; кнопки Подробнее · 👍 · 👎 · 🔕.
- Приоритет CRITICAL — визуально выделен, но не «кричащий баннер ради баннера».

### 5.9. Настройки, Поход, Сравнение, Окно выхода
- Настройки: часовой пояс, тихие часы (по умолч. 22:00–07:00), чувствительность
  low/normal/high, язык, единицы.
- Trip-мастер: название → точки (1..10) → даты → размер группы (пошагово, с кнопкой
  отмены на каждом шаге).

## 6. Визуальная система

### Цвет = семантика надёжности (главная цветовая шкала)
- 🟢 ≥ 70 — «надёжно» · 🟡 40–69 — «ориентировочно» · 🟠 25–39 — «низкая» ·
  🔴 < 25 — «не опираться». **Цвет всегда дублируется словом и/или формой.**
- Осадки — отдельная нейтрально-синяя шкала интенсивности; не смешивать со шкалой
  надёжности.
- Дальний горизонт — понижение насыщенности/контраста (принцип P4).

### Типографика
- Крупная, читаемая на солнце; числовые значения — табличные цифры (моноширинные
  цифры) для выравнивания колонок осадков.
- Иерархия: значение p50 — акцент; разброс и вспомогательное — приглушённый вес.

### Компонентная библиотека (спроектировать как переиспользуемые)
- **ReliabilityBadge** (цвет + число/статус + слово).
- **ConsensusDayRow** (день · HIL · `p50 (p10–p90)` · POP-бар · %).
- **PrecipRangeBar** (p10–p90 как лента, p50 как метка).
- **HILChip** (0–5, иконка + подпись).
- **DegradedModelsBadge** (`4/5 моделей`).
- **Meteogram**, **EvolutionHeatmap**, **ModelSpaghetti**, **ChangeCard**, **TripCard**.

### Движение
- Сдержанное: переходы 150–250 мс; скелетоны; без «прыгающих» цифр. Изменение
  значения — мягкий морф, подчёркивающий «стало иначе».

## 7. Состояния (обязательны для каждого экрана)
- **Загрузка** — скелетоны структуры карточки.
- **Пусто** — понятный призыв к действию.
- **Ошибка сети** — «не удалось обновить, показываю последнее от HH:MM».
- **Прогноз не рассчитан** — «конвейер ещё не отработал».
- **Деградация** — `N/5 моделей`, надёжность снижена, явная пометка.

## 8. Что отдать в Claude design (формат результата)
- Один HTML-артефакт: **галерея экранов в мобильном фрейме** (≈390×844), плюс
  показать 2–3 экрана в десктоп-раскладке.
- Обе темы (светлая/тёмная) — переключатель в артефакте.
- Реальные данные из §0 (Ачишхо/Аибга, поход «Ачишхо→Аибга», примеры осадков и POP).
- Для каждого экрана — подпись: какую user story / JTBD закрывает (ссылка на PRD §6).
- Начать с короткого списка экранов и почему; уточняющие вопросы — только если
  чего-то принципиально не хватает; затем собрать артефакт.
- При конфликте с текстом — приоритет у [PRD.md](../../PRD.md).
